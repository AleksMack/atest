# Стратегия тестирования: полный товарно-финансовый flow (CTRM)

Подробная последовательность демонстрации и проверок по трем сессиям описана в
`SCENARIO.md`. Этот документ фиксирует техническую стратегию автотестов и модель
данных, а `SCENARIO.md` является бизнес-чек-листом от входа до финансового итога.

## Что тестируем

Один изолированный сквозной flow проходит полный путь товара и денег:

`контракт -> сделка покупки -> логистика -> склад -> продажа -> инвойс -> платеж -> банковская выписка`

### 1. Контракт

Создается уникальный контракт на продукт из текущего flow с поставщиком, объемом,
закупочной ценой и валютой. В `FlowContext.purchaseContract` сохраняются его
номер, параметры и идентификатор.

### 2. Сделка покупки

Создается purchase trade по тому же контракту. Проверяем, что продукт,
контрагент, объем, цена и валюта совпадают с контрактом. Идентификатор сделки
сохраняется в `FlowContext.purchase.trade`.

### 3. Логистика

Для той же сделки создается коносамент на тот же продукт и тот же танкер
из текущего flow. Вводится фрахт именно этого судна. Проверяем связь коносамент ->
сделка и совпадение продукта и объема. Идентификаторы сохраняются в контексте.

### 4. Склад и себестоимость партии

Выполняется операция прихода. На складе появляется партия с тем же продуктом,
танкером и объемом. Проверяем, что партия связана с операцией прихода, а система
рассчитала себестоимость:

`полная себестоимость = стоимость покупки + фрахт + прочие затраты`

Проверяем себестоимость единицы и всей партии. Партия и ее стоимость сохраняются
в `FlowContext.warehouse` и `FlowContext.economics`.

### 5. Продажа

Создается sales trade на продукт из складской партии. Объем продажи не может
превышать доступный остаток. Выполняются коносамент и операция отгрузки.
Проверяем списание проданного объема со склада и сохранение остатка.

### 6. Инвойс

По сделке продажи создается инвойс на тот же продукт, объем и сумму продажи.
Проверяем связи инвойс -> sales trade и совпадение валюты и суммы.

### 7. Платеж

Создается платеж по инвойсу на ту же сумму и валюту. После проведения статус
инвойса меняется согласно бизнес-правилу, а платеж получает подтвержденный
статус. Идентификаторы и статусы сохраняются в контексте.

### 8. Банковская выписка

Выписка импортируется или создается для этого платежа. Проверяем связь
выписка -> платеж, сумму, валюту и статус сверки.

### 9. Итог по сделке

В отчете или карточке сделки проверяем:

- закупочный объем, проданный объем и остаток;
- стоимость покупки, фрахт и прочие затраты;
- полную себестоимость партии и себестоимость единицы;
- выручку по продаже;
- финансовый результат: `результат = выручка - полная себестоимость проданного объема`;
- маржинальность, если она рассчитывается системой;
- связность всех документов и отсутствие другой партии или другого танкера.

## Выбор инструмента

Основной инструмент: **Playwright + TypeScript**.

Обоснование: сценарий описан как последовательность действий пользователя в браузере
(логин, заполнение форм, чтение отчета), а не как набор вызовов API. Postman тестирует
API-контракт, но не проверяет форму, валидацию, рендеринг и интеграцию фронта с бэком,
то есть не отвечает на вопрос "может ли пользователь пройти сценарий в приложении".

API (есть Swagger) используется как вспомогательный слой:
- подготовка тестовых данных для шагов, которые сами по себе не являются предметом проверки;
- при необходимости, сверка отображаемого в UI значения с значением, которое вернул бэкенд
  (для расчета цены на шагах 5 и 9).

Критичные шаги (ввод коносамента, расчет цены, отчет) проверяются через UI в любом случае.

## Ограничения среды, принятые как есть

| Ограничение | Решение | Последствие |
|---|---|---|
| Нет `data-testid` на элементах | Локаторы по роли/лейблу (`getByRole`, `getByLabel`), где возможно | Тесты чувствительны к изменению текста и структуры экрана, поддержка потребует больше времени при каждом релизе. Технический долг зафиксирован, не скрыт |
| Сброс тестовой среды дорогой | Тесты не зависят от чистого состояния: каждая сущность создается с уникальным суффиксом (timestamp/random), тест ищет свои данные по этому суффиксу, а не по позиции в списке | Тесты можно гонять повторно без очистки среды; накопление тестовых данных в среде остается открытым вопросом (нужна точечная очистка через API, если бизнес-логика это позволяет) |
| Логин через UI каждый раз | Не оптимизируем через API/токен | Тест медленнее, но логин-форма проверяется как часть каждого прогона, это сознательный выбор |
| CI пока не настроен | Только локальный запуск | Структура проекта не зависит от способа запуска, CI можно добавить позже без переписывания тестов |

## Архитектура

```
tests/
  e2e/            сам сценарий, тонкий, читается как чек-лист шагов
  steps/          переиспользуемые действия пользователя (createPurchaseTrade, enterBillOfLading, ...)
  pages/          Page Object для экранов со сложной внутренней логикой
  api/            типизированный клиент из Swagger, фикстуры для подготовки данных
  utils/          генерация уникальных тестовых данных, контекст flow, общие хелперы
```

Принцип: сценарий в `e2e/` не содержит локаторов и деталей реализации, только
последовательность вызовов из `steps/`. Изменение конкретного экрана правится
в одном файле в `steps/` или `pages/`, а не во всем тесте.

## Контекст данных flow

Каждый сквозной сценарий создает собственный `FlowContext` через
`tests/utils/flow-context.ts`. В нем хранятся общие бизнес-данные flow
(`product`, `vessel`, `freight`, `volume`), контракт, параметры покупки и продажи,
складская партия, инвойс, платеж, банковская выписка, экономика flow, а также
идентификаторы созданных сущностей. Для справочников сохраняются отдельные `id`
выбранных записей (`commodity`, контрагенты, валюта, единицы измерения, порты,
условия поставки и оплаты, склад, банк), а не только отображаемые названия.

Шаги получают этот объект и дополняют его идентификаторами после создания сущности.
Поэтому коносамент и операция используют тот же продукт и танкер, что и сделка,
а следующий шаг не ищет данные заново по спискам. Контекст создается отдельно для
каждого теста и не является глобальным состоянием, что сохраняет изоляцию при
параллельном запуске.

Общие справочники не создаются в каждом E2E-тесте. Они один раз подготавливаются
в тестовом проекте. В UI тест может находить записи по имени в списках и dropdown,
но после выбора должен сохранить полученный `id` в `FlowContext` или использовать
его из network/API response. Каждый flow создает только свои транзакционные
сущности и не меняет общие записи.

## Порядок расширения

1. Контракт и сделка покупки.
2. Логистика, приход на склад и расчет себестоимости.
3. Продажа и списание партии.
4. Инвойс, платеж и банковская выписка.
5. Сверка себестоимости, выручки и результата сделки.
6. Вариативность: частичная продажа, разные Incoterms, ошибки валидации.

## Открытые вопросы (не закрыты в рамках этого обсуждения)

- Точечная очистка тестовых данных после прогона: возможна ли отмена/аннуляция
  каждой сущности через API.
- `data-testid`: запрашивать ли у разработки хотя бы на ключевые элементы сценария,
  или жить с текущим риском постоянно.
- CI: когда и на чем запускать (обсуждается отдельно, вне рамок текущей стратегии).
