# Пошаговая стратегия развития тестового набора

Детализация раздела "Порядок расширения" из `STRATEGY.md`. Каждый шаг закрывается
до перехода к следующему: критерий готовности явный, чтобы не размывать объем.

## Шаг 0. Подтверждение каркаса (готово)

- [x] Playwright + TypeScript, структура `tests/e2e|steps|pages|api|utils`
- [x] Конфиг, алиасы путей, `tsc --noEmit` без ошибок
- [x] `playwright test --list` видит сценарий

Критерий готовности: команда может добавлять код в существующую структуру, не создавая свою.

## Шаг 1. Login + создание сделки покупки

- [ ] Подготовить отдельный setup Master Data и проверять наличие активных записей
  перед запуском flow, не создавая справочники в каждом тесте
- [ ] Заполнить локаторы `LoginPage` под реальный экран (уже частично готово, свериться)
- [ ] Прогнать `login()` вживую, зафиксировать реальный признак успешного входа в `expectLoggedIn()`
- [ ] Открыть форму создания сделки покупки, собрать список реальных полей
- [ ] Заполнить `TradeFormPage.create()`, вернуть id/номер сделки
- [ ] Создать контракт и связать его с purchase trade
- [ ] Прогнать шаги 1-2 сценария изолированно (отдельный тест или `test.step`)

Критерий готовности: `login + createPurchaseTrade` проходит зеленым на реальном стенде.

## Шаг 2. Коносамент, оприходование и складская партия

- [ ] Собрать поля формы коносамента, заполнить `BillOfLadingPage.enter()`
- [ ] Собрать элементы экрана операции оприходования, заполнить `OperationsPage.run('cargo-receipt', ...)`
- [ ] Найти, где и как отображается рассчитанная цена покупки, заполнить `PriceCalculationPage.getCalculatedPrice()`
- [ ] Решить: проверять цену только через UI, или сверять с ответом API (если есть эндпоинт)
- [ ] Зафиксировать складскую партию, остаток и полную себестоимость
- [ ] Прогнать цепочку контракт -> покупка -> логистика -> склад

Критерий готовности: ветка покупки создает связанную складскую партию и возвращает
проверяемую себестоимость.

## Шаг 3. Продажа и списание партии

- [ ] Проверить, что `TradeFormPage.create('sale', ...)` работает без изменений (форма та же) или требует доработки
- [ ] Проверить предусловие: sales trade не создается без существующего cargo/batch (см. domain constraint в ways-of-working), тест должен явно на это полагаться, а не полагаться на побочный эффект
- [ ] Повторно использовать `BillOfLadingPage`, `OperationsPage` с типом `'sale'`
- [ ] Заполнить `PriceCalculationPage` для цены продажи, если отличается от покупки логикой отображения
- [ ] Проверить остаток партии до и после продажи
- [ ] Прогнать цепочку до продажи целиком

Критерий готовности: полный цикл покупка-продажа проходит зеленым без ручного вмешательства.

## Шаг 8. Вариативность сценария

Только после того, как базовый цикл стабилен (шаги 0-5 закрыты). Иначе вариации множат
хрупкость поверх нестабильного основания.

- [ ] Частичная продажа (Partial Sale / Bill of Lading Realization)
- [ ] Разные Incoterms (в демо использовался FOB, проверить другие в рамках MVP)
- [ ] Негативные кейсы: отсутствие cargo/batch при попытке создать sales trade, невалидные данные в форме
- [ ] Third-Party Payments, если войдет в MVP (сейчас открытый вопрос в проекте, см. `/areas/optiflow.md`)

Критерий готовности: определяется отдельно после согласования, какие вариации приоритетны.

## Правило при изменении сценария в приложении

Если бизнес-процесс меняется до завершения шага, на котором сейчас работа:
1. Зафиксировать изменение в `CHANGELOG.md`.
2. Оценить, ломает ли изменение уже написанный код текущего шага, или только будущих шагов.
3. Не переписывать весь сценарий на лету: править конкретный `step`/`page`, где изменение,
   остальное не трогать (совпадает с принципом целевых правок из ways-of-working).
